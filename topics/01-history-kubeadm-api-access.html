Install a cluster with kubeadm

kubeadm bootstraps a conformant cluster. It does not provision machines and it does not install a network plugin. You bring the nodes, a container runtime and a CNI; kubeadm creates certificates, kubeconfigs and the control plane as static Pods.

Requirements & ports

  • A CRI runtime: containerd or CRI-O

What kubeadm init actually does

Press play. Each phase can also be run alone with kubeadm init phase <name>.

root@cp1
$ sudo kubeadm init --pod-network-cidr=10.244.0.0/16
⚠️
Node stays NotReady after init? Expected. kubelet reports NotReady until a CNI plugin is installed. CoreDNS Pods also stay Pending until then.
💡
Lost the join command? Bootstrap tokens expire after 24 h. Run kubeadm token create --print-join-command on the control plane for a fresh one.

Kubernetes API groups & versions

Every object is a REST resource. Resources are organised by group and version. The apiVersion field in YAML is exactly group/version, or only v1 for the core group.

Anatomy of an API path

Version maturity

alpha · v1alpha1
  • Disabled by default (feature gate)
  • May change or vanish in any release
  • Never in production
beta · v1beta1
  • New beta APIs are off by default since 1.24
  • Schema may still change
  • Deprecated, then removed after GA ships
stable · v1, v2
  • Enabled by default
  • Backwards-compatible within the major version
  • Use these for real workloads

Access the cluster as a new user (CSR + RBAC)

Kubernetes has no User object. A "user" is whatever an authenticator says. With X.509 client certificates, the cert's CN becomes the username and each O becomes a group. Any cert signed by the cluster CA is trusted.

Animated flow: from private key to allowed request

Hands-on: create user jane

Request pipeline simulator

jane has Role pod-reader in namespace dev (get, list, watch, create on pods). Pick a request and send it through the API server.

# waiting for a request…
⚠️
You cannot revoke a client certificate. Kubernetes does not check a CRL. If jane's key leaks, the cert works until it expires. Remove access by deleting the RoleBinding, and always set a short expirationSeconds. For real teams, prefer OIDC (SSO) for humans and ServiceAccount tokens for workloads.
💡
Bind groups, not people. The cert's O=dev-team lets you write one RoleBinding with --group=dev-team. New team members then only need a cert, not a new binding. Never use O=system:masters: that group bypasses RBAC entirely.

Summary

Key ideas to keep, a one-screen cheat sheet, and a quick self-check.

Cheat sheet

bootstrap
# all nodes
swapoff -a; modprobe overlay br_netfilter; sysctl --system
apt-get install -y containerd kubelet kubeadm kubectl
# control plane
kubeadm init --pod-network-cidr=10.244.0.0/16
cp /etc/kubernetes/admin.conf ~/.kube/config
kubectl apply -f <cni.yaml>
kubeadm token create --print-join-command
# workers
kubeadm join cp1:6443 --token … --discovery-token-ca-cert-hash sha256:…
api + user access
# explore API
kubectl api-versions
kubectl api-resources -o wide
kubectl explain pod.spec --recursive
# user via CSR
openssl genrsa -out jane.key 2048
openssl req -new -key jane.key -subj "/CN=jane/O=dev-team" -out jane.csr
kubectl apply -f csr.yaml   # signerName: kubernetes.io/kube-apiserver-client
kubectl certificate approve jane
kubectl get csr jane -o jsonpath='{.status.certificate}' | base64 -d > jane.crt
kubectl create rolebinding … --role=pod-reader --user=jane -n dev
kubectl auth can-i list pods -n dev --as=jane
